## 一、结论

0.12.0 的报告重构与插件工作区已经实现，并通过本地单元测试、隔离 HTTP 验收、大图验收和报告页面浏览器验收。尚未做真机验收（真实 QQ 群发送、真实模型 provider）；工作区管理页按桌面宽度交付，未做手机宽度验收。

## 二、本轮交付范围（0.12.0）

- 报告：概览 / 全部图片 / 按人查看三层结构，图册与列表视图、图片明细页、明暗主题、搜索与筛选、分歧排序，以及少票、零票、已展示未获票、发送失败、未展示等状态；目录版与单文件版都可离线打开。
- 报告数据：口径升到 v2，含逐人最终评分、总体标准差、以成功展示图片为分母的覆盖率；汇总分享模式在序列化时移除个人明细与群号。
- 头像：QQ 头像派生缓存，限制下载大小、输出尺寸与并发，失败回退姓名首字；单文件报告内嵌头像，缓存文件名不暴露 QQ 号。
- 插件工作区（Plugin Pages）：运行控制、项目登记与目录浏览、预检、历史报告、报告预览、HTML / ZIP 下载、分组配置保存与版本冲突检查；接口要求当前 Dashboard 管理员身份，卸载时释放本实例的路由与导出任务。
- AI：提示词模板可配置与预览，`/vote export --ai` 显式重新生成总结，模型调用超时降级。
- 可靠性：重新导出先生成临时产物，失败保留旧报告；报告失败在历史中可见；清理后可从未删除的评分重新生成。

## 六、2026-09-14 修复

代码审查提出四条 P1，其中三条复现并修复；第四条按原描述不能复现，改为原子实现：

1. 并发导出竞态：`export()` 在参数校验的 await 之前先占用 session_id，两个并发请求只有一个能启动生成，另一个收到「该报告正在生成」。
2. 配置保存失败未回滚磁盘：保存抛错时在还原内存的同时把配置文件写回保存前的内容（版本冲突除外），避免后续 `_ensure_config()` 加载这份「没保存成功」的配置。
3. 下载 / 预览与清理竞态：读取期间登记 readers，清理接口在有人读取时拒绝执行；单文件下载先打开文件句柄再流式返回，清理删除目录不会打断下载。
4. 改名非原子：原描述是「目录项目改名后报错、但新登记已落盘」，实测 `unregister` 对未登记的名字返回 `False` 而不抛错，因此不会出现该报错；但「先登记新名、再移除旧名」确实是两次写入，现在由 `ProjectRegistry.register(..., drop_name=)` 在一次写入里完成。
5. 报告手机宽度：按人查看页在 390px 视口下横向溢出到 692px（`.report-grid` 的列被缩略图固有宽度撑开），改为 `minmax(0, 1fr)` 并给 `.people-layout` 子项加 `min-width: 0`。

对应新增回归测试 5 项，测试总数 93 → 98。

## 七、2026-09-15 修复

交叉审查又报了两条跨入口的 P2，均已复现并闭合：

1. 群命令清理绕过下载保护：`/vote cleanup` 直接调用应用层删除，不检查报告是否正在被读取或生成。
2. 页面清理与导出仍有竞争窗口：页面清理检查完导出占位后要等数据库，而占位不持有同一把锁，导出已进入生成时清理仍会删掉旧报告。

修法是把报告读取、生成与清理的互斥统一收到应用层的 `ReportActivity`（`src/report_activity.py`），网页工作区与群命令共用同一实例：导出在守卫里先占位（发生在校验的 await 之前），清理在删除前同步标记；三种状态互斥，且状态变更都是同步的，因此在 asyncio 单线程里天然原子。清理结果改为 `CleanupResult(removed, skipped)`：`/vote cleanup all confirm` 跳过使用中的报告并在回复里说明，定向清理则直接报错。

新增回归测试 3 项（读取期间清理、生成期间清理、清理期间导出与读取），测试总数 98 → 100。

## 八、2026-09-15 真机验收与修复

在 NAS 的真实实例（AstrBot 4.28.0 + NapCat，容器 6185 / 6099）上完成了第一轮真机验收：

- 插件从 `44e0ce7`（0.10.0）快进到当日 `main`，重载后装配正常，数据库自动补列。
- 通过工作区接口逐项验收：配置读取与保存（含过期版本 409 与落盘核对）、项目列表、`重聚` 预检（15 张 / 60 MB，`Thumbs.db` 被识别为无效文件）、群列表（经 NapCat 实取）、历史场次、单文件报告下载（2.24 MB 流式返回）与内嵌预览。
- 真实投票一场（`11BA81D9`，重聚，15 张，2 位参与者，11 票）：报告与数据库逐张逐票核对，0 处不一致。

这轮真机验收发现并修复了三个问题（0.12.1）：

1. 候选角色从未落库：重建候选时漏了 `character` 字段，`character_name` 全库为空，角色合并统计只能靠标题兜底；带 `project.json` 角色映射的项目会统计错。
2. 投票人名字与群里不一致：AstrBot 的 aiocqhttp 适配器按 `nickname or card` 取值，报告显示 QQ 昵称而不是群名片。
3. 被忽略的投票没有痕迹：超出范围、引用其他场次、本场不收票等情况静默丢弃，事后无法对账；现在逐条记录原因，并记录每条计票的图片、分数与是否覆盖旧票。
