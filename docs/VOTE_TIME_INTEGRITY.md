# 投票时间一致性与计票完整性方案

> 状态：本节所述小范围修复已包含在 0.13.18，随本次 `main` 发布部署；真实群投票验收由用户明确推迟到下一次投票。后文保留事故分析与原始完整候选方案，其中历史回扫、队列观测和完整事件明细尚未实施。
> 起因：2026-10-20 一场 130 张图片、18 位参与者的投票出现大面积人物错位；本次数据报告已单独修正。

## 本次实现及边界

- 新场次保存 `time_routing` 与覆盖策略快照，使用 `vote_windows` 记录开放、关闭时间。同一人物的连续图片共用窗口；切换人物时关闭上一窗口，发送空档不接收普通数字票。引用票按本场图片定位，不受人物窗口关闭影响，整场截止约束同时适用于两种票。
- 本机窗口起止与 `AstrMessageEvent.created_at`（限流前的事件创建时间）比较。OneBot `time` 和 `real_seq` 单独保存；开窗时优先用真实消息顺序核验图片是否已经发出，处理图片先显示、发送回执后返回的情况。普通票来源保留该时刻最近成功发送的同人物图片；合并发送保留该条消息的首张来源。
- 最终票新增原始消息时间、真实顺序、接收时间字段；有真实序号时优先比较序号，否则按原始时间与接收顺序判断。重复消息不会重复改分，未胜出的旧票不会更新分数、来源图片和时间。处理入库时间继续单独保留。
- aiocqhttp 群发图读取发送消息身份及有界超时的 `get_msg` 元数据；其他平台复用原发送路径。元数据读取失败记录警告、保留成功发送结果，使用本机确认时间保守判断；缺少真实序号时，同秒且早于回执的边界票不能保证恢复。
- 收票入口在第一次 await 前登记，等待发图回执和窗口落库后再路由。结算固定截止点，允许已登记、原始接收时间早于截止的评分（含引用票）写入，再封存统计；取消的收票任务也必须等已开始的 SQLite 写入完成。AI 和报告在封存后生成，不在数据库事务内调用网络服务。
- 图片回执、进度及开窗记录原子提交。数据库升级只增加字段和窗口表，不回填未知的原始时间，不重算已完成历史报告；旧版本遗留的中断场次恢复时仍使用旧路由，结束后新开场次使用新规则。回退旧代码时保留新增字段和表即可。
- 当前单群运行的 AstrBot 限流已只读确认保存为 `60 秒 / 300 条 / stall`。本修复不会读取或等待 AstrBot 限流阶段尚未进入插件的消息；上游丢失、跨进程中断和封存后才到达的输入，仍需后续历史回扫才能补偿。

后文的“最近一个 sent_at”是原始候选思路，不是本次最终实现；实际路由以本节明确的窗口和时间口径为准。历史回扫如需实施，必须另行解决平台时间与本机接收窗口的边界对账，不能直接混用。

## 1. 事故事实

- 目标实例：AstrBot 4.29.1；每群限流配置为 60 秒 30 条，策略 `stall`。
- 受影响场次共 130 张图片、63 个人物、18 位参与者，开始时长为 24 分钟。
- 某人物窗口内出现 7 条裸 `10` 和 1 条 `2`；这些消息在 78–85 秒后才被当前窗口处理器执行，最终记到了后续两个人物名下。
- 该人物最终保留了 3 条低分票；追溯原始消息，它们分别属于更早的两个人物窗口。
- 按日志中的事件时间与图片发送时间对账：444 条当前窗口处理记录中，395 条目标人物不一致；延迟中位数 69.6 秒，90 分位 196.5 秒，最大 223.1 秒。
- 原报告 440 票；从原始事件按图片窗口重建后为 560 票。差异同时包含错位覆盖和结算前未排空。

## 2. 根因边界

### 2.1 直接诱因

AstrBot 在消息进入插件前执行按会话限流。配置为 30 条/60 秒且采用 `stall` 时，超出部分会排队，可能导致事件延迟几十秒到数分钟才到达插件处理器。

### 2.2 核心缺陷

普通数字票当前按“插件开始处理的时刻”读取 `session.active_character`，而不是按“用户发出消息的时刻”判断目标人物。图片发送循环仍在继续，处理延迟跨过人物切换后，票就会被归到后来的人物。

### 2.3 第二个缺陷

即使把人物归属改成原始时间，如果 `last_wins` 仍按数据库写入/处理顺序覆盖，晚处理但更早发送的票仍可能覆盖更晚发送的票。人物归属和冲突顺序必须使用同一时间基准。

### 2.4 完整性问题

限流仍可能造成结算前队列未排空。只改时间归属能修复错位，但不能保证所有已发送且在截止前的票都进入报告。

## 3. 设计原则

1. 投票目标只由消息原始接收时间和图片发送时间线决定；处理时间不参与目标判断。
2. 同一用户同一人物的最终票按消息原始时间应用 `last_wins`、`first_wins`、`max_score`、`min_score`。
3. 时间无法解析、早于首张成功图片或晚于截止时间时，拒绝并记录明确原因，不猜测当前人物。
4. 引用票仍按被引用图片的会话标记定位，不随当前窗口变化；其格式扩展另行决策，不混入本方案。
5. 结算前必须等待可确认的投票输入排空；如果当前 AstrBot 接口无法确认队列状态，则必须通过限流配置或新的前置入口消除未排空风险。
6. 修复必须保留旧场次和旧报告，迁移不可破坏历史数据。

## 4. 推荐实现

### 4.1 时间来源

- 使用 `AstrMessageEvent.created_at` 作为首选接收时间。该字段在 AstrBot 事件对象构造时写入，早于限流流水线的排队等待。
- 若平台提供 OneBot `message_obj.raw_message["time"]`，可同时保存做交叉校验；生产路由以事件的原始接收时间为准。
- 统一转换为 UTC epoch 秒或毫秒后比较，不直接比较字符串。

### 4.2 人物窗口解析

当前 `candidates.sent_at` 已记录发送确认时间，可以作为图片时间线。新增一个纯函数：

```text
resolve_character_at(candidates, event_time)
  -> 最后一个 sent_at <= event_time 的成功发送候选
  -> 使用该候选的 character_name 和 id
```

该规则自然覆盖：

- 同一人物的多张图片；
- 最后一张图片之后、下一个人物首张图片之前的等待期；
- 队列延迟已经跨过后续人物的情况。

首张成功图片之前的时间不开放普通票；截止时间之后的时间不参与本场结算。

### 4.3 票的目标与顺序

- 普通数字票：用 `resolve_character_at` 返回的候选与人物构造 `VoteDecision`，不再使用处理器执行时的 `session.active_character`。
- 引用票：继续使用被引用图片所属人物。
- 新增 `votes.message_time` 可空字段，保存消息原始时间。
- 写入时按 `(session_id, character_name, voter_id)` 查找现有票：
  - `last_wins`：仅当新 `message_time >=` 旧值才覆盖；
  - `first_wins`：仅当新 `message_time <` 旧值才替换；
  - `max_score` / `min_score`：先比较分数，同分时按事件时间决定来源与时间；
  - 旧数据没有 `message_time` 时，回退到原有处理时间，不参与新场次的严格时间判断。
- `created_at` 保留处理入库时间，`message_time` 单独表达用户发送时间，避免混淆诊断语义。

### 4.4 截止与队列排空

时间归属只解决“延迟后记给谁”，不能保证截止前所有票都已完成处理。建议按顺序评估：

1. 首先调整 AstrBot 的会话限流，给当前群足够余量。30/60 明显低于 18 位参与者连续评分的峰值；建议在受控群提高到峰值以上，或确认可以关闭该群的 `stall` 限流。
2. 调查 AstrBot 是否提供限流前的事件钩子或可查询的流水线空闲信号。若有，投票入口应使用该钩子或等待其排空。
3. 若没有前置钩子，增加明确的结算等待/重试策略：截止后延迟一小段时间再锁定计票；但这只能降低风险，不能证明队列为空，不能作为唯一保证。
4. 报告生成前检查投票活动守卫；结算后、导出前记录 `late_after_cutoff` 指标，发现迟到票时拒绝生成“完整”报告或标记待复核。

### 4.5 截止后历史消息回扫

可以在报告生成前增加一次有限范围的历史回扫，作为实时路由之外的补偿层；它不应替代 4.1–4.3 的时间归属修复。

- 当前 NapCat 构建包含 OneBot 扩展动作 `get_group_msg_history`，参数至少包括 `group_id`、`message_seq`、`count`、`reverse_order`。实现前应在目标版本用只读调用确认返回的 `time`、`message_id`、`message_seq`、sender 和消息段结构。
- 只扫描本场 `group_id`、`started_at` 到 `finished_at` 的消息；不读取其他群，不持久化聊天正文，只保留投票所需字段。
- 普通数字票用消息 `time` 按图片 `sent_at` 时间线重新归属；引用票按被引用图片的会话标记归属。
- 用 `message_id` 去重，避免实时处理和回扫重复计票；最终票仍按原始消息时间执行重复票策略。
- 回扫必须在截止后、报告生成前完成，并设置总时限、最大页数和总消息上限，避免大群历史拖死结算。
- 回扫失败或超时不阻塞报告，但必须写入 `history_reconciliation=failed/timeout` 和可见警告，不能静默声称结果是完整的。
- 回扫发现变更时，先在同一事务中写入修正后的最终票，再生成 HTML/AI 总结；不要先生成报告再补票。

### 4.6 可观测性

每次普通票记录以下字段到日志：

- 原始事件时间与处理时间；
- 延迟毫秒；
- 解析出的人物、图片序号；
- 是否跨过人物窗口；
- 覆盖原因与旧票时间。

每场结束输出汇总：处理延迟 p50/p90/max、拒绝票数、截止后票数、无法解析时间票数。达到阈值时告警，而不是静默生成报告。

### 4.7 数据迁移

- 只追加 `votes.message_time` 可空列和必要索引，不重建历史票表。
- 旧票 `message_time` 保持 `NULL`；报告继续按现有字段工作。
- 新票写入完整时间；旧报告不自动重算，避免把不可验证的处理时间伪装成发送时间。
- 本次已修复场次保留独立备份，不参与迁移重写。

## 5. 验证与验收

### 5.1 单元测试

- 消息在人物 A 窗口发送，但处理时人物已切到 C：必须记到 A。
- 两张图片之间、最后一张后等待期、下一个人物首图之后各一条消息：人物边界正确。
- 同一用户同一人物先发 10、后发 3，但处理顺序颠倒：最终必须是后发的 3。
- `max_score` / `min_score` 同分时按原始时间选择来源票。
- 缺失时间、首图前、截止后的票被拒绝且日志原因正确。
- 引用票不受普通票时间解析影响。

### 5.2 集成场景

- 模拟 18 位用户、30 条/60 秒限流持续突发，验证不出现跨人物归属。
- 对 130 张图片、63 人物、截止前排队消息重放，比较报告票数与原始有效票。
- 若 AstrBot 无法提供排空信号，同时验证提高限流后的峰值余量，并明确残余风险。
- 用 NapCat 历史接口回放同一时间窗，验证 `message_id` 去重、分页边界、接口超时和无法获取历史时的降级标记。

### 5.3 真实验收

- 先使用测试群和较小项目，记录原始聊天中的分数、报告排名和数据库票行。
- 再进行一次真实高峰场次；至少对照某个人物的全部分数，确认票数、均分、分布和来源图片一致。
- 不以“代码已部署”或“测试通过”代替真群验收。

## 6. 实施顺序与回退

1. 先加时间字段、解析函数和日志，不改默认行为；在测试中重放历史事件。
2. 切换普通票路由并改为按事件时间应用重复票策略；完成回归。
3. 调整限流与结算排空策略；确认峰值余量。
4. 发布到测试群，观察一至两场，再部署 NAS。
5. 部署前备份数据库与配置；迁移只追加列。回退代码时保留新列即可，不删除数据。
